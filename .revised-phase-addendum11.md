```python
RENDER_TRANSFER_SPEC: dict   # provenance, exported by both families

def render_transfer_power(freqs_hz, *, sample_rate_work, sample_rate_out=16000) -> np.ndarray
```

- `freqs_hz`: real `(F,)` **output-band** frequencies in Hz, `0 .. sample_rate_out/2`, with
  `F = n_fft_analysis//2 + 1`.
- Returns `(F,)` real **dimensionless POWER gain** `|H(f)|^2` (already squared, linear, not dB),
  approximately 1 in the passband.
- Composes, **in the order the renderer actually applies them**: (1) the render AA FIR designed at
  `sample_rate_work` (7900 pass / 8000 stop / 100 dB / 0.01 dB ripple) — reuse
  `antialias_filter`, do not design a second filter; (2) the **UNCHANGED** `resample_poly` FIR for
  `sample_rate_work -> sample_rate_out`.
- Reproduce the decimator's filter **deterministically from the rates**, not hardcoded:
  `g = gcd(work, out)`, `up = out//g`, `down = work//g`, `max_rate = max(up, down)`,
  `f_c = 1/max_rate`, `half_len = 10*max_rate`,
  `h = firwin(2*half_len + 1, f_c, window=('kaiser', 5.0)) * up`.
  For 64000 -> 16000: `up=1, down=4`, 81 taps, `f_c=0.25`. **State the `*up` upsampling-gain
  convention in the docstring** so a future `up != 1` cannot silently rescale.
- **`aa_application` is a SINGLE PASS**, so the AA contributes `|H_aa|^2` in power, **not**
  `|H|^4`. Your rewrite is one centered `oaconvolve` application, so this matches; record
  `aa_application="single_pass_centered_fir"` in `RENDER_TRANSFER_SPEC`.
- Put the **alias floor in `RENDER_TRANSFER_SPEC` as a COMPUTED number**, not an assertion:
  evaluate the designed response at the folding frequencies for 4:1 and store the **worst-case**
  attenuation of anything folding into 0..8000, alongside the >= 100 dB expectation.
- No fit parameter, no stochastic mechanism. `clips.decimate` is only **modelled**, never
  replaced.

**Apply it EXACTLY ONCE** — in the candidate fit, the candidate predict, and **your legacy

**Label it honestly:** this is a **WINDOW/FILTER-COMMUTATION APPROXIMATION**, not an exact

### Why the transfer belongs inside the fit (do not re-derive or second-guess this)

The fit sees real 16 kHz data `D` and models `M = T * S(params)`, so it learns `S` such that
`T*S ~ D`. The renderer synthesizes `S` at 64k and then **physically** applies `T`, so the
synthetic arm reproduces `D` in the analysis band regardless of the real clip's own 44.1 kHz
history. This is self-consistent, not a fudge.

The consequence to state plainly wherever levels are reported: **`S` itself is not a physical
source spectrum in absolute terms.** Never let `profile_db` be read as a calibrated source level.
