## 1. Raw-track guard (P1, CLI)

`rps_key` is passed through to `load_clip` verbatim, so `rps_refined` — or `auto`, which
`clips.py` resolves to `rps_refined` first — would fit the candidate on inferred labels, which this

## 2. Unbiased minibatch scale (P1)

With duplicate-window splitting the frame weights are unequal, and the current
`weights.sum() / weights[fi].sum()` is a **self-normalized** estimator, not the unbiased estimate
of the full risk it claims to be: with one sampled frame every selected loss gets the same total
exposure regardless of its own weight, so duplicated windows regain disproportionate influence and
the MAP target moves whenever `frames_per_step` is set.

Main's minimal choice: **uniform sampling without replacement, retain each selected frame's own
weight, and scale by `N_full / N_sampled`.** Keep the weights, change only the scale. Say in a
comment that this is unbiased for uniform sampling and that the self-normalized form was not.

## 3. Duplicate/overlapping training supports: REJECT, do not share (P1)

Duplicated frame keys already split their composite weights, but each manifest row still gets its
own `state_innov` block and its own bias with a full prior, so repeating a clip turns
`loss + prior` into two half-losses plus **two** priors — extra shrinkage, i.e. duplicates
smuggling in information after all.

Main's minimal choice is explicit: **reject duplicate or overlapping TRAINING supports before
allocating any state/bias block** — do NOT build a shared-state/shared-bias framework keyed by
recording time. Validate the manifest's clip list per rig: two rows of the same
`(dataset, recording)` whose `[start_s, start_s + seconds)` intervals intersect, or are identical,
are an error naming both rows. Held-out/predictive use of overlapping windows is unaffected; this
guard is for the fit cohort only.

## 4. Moment stage: per-microphone, per-frame gating (P1 + P2)

Two related defects:

- The SNR gate is computed **after averaging power across microphones**, then every microphone's
  phase residual is pooled equally. An order strong in some channels and noise-only in others
  passes the 10 dB gate while the weak channels contribute nearly uniform phase, inflating the
  fitted OU/`D` moments.
- Only the **median** SNR of the whole track is tested, and `min_frames` is compared against the
  clip's total frame count, so a track with just over half strong frames passes and every weak
  frame — and every lag pair straddling weak frames — still enters the variance.

Main's minimal choice: **per-MIC, per-FRAME SNR mask plus continuous-valid-run lag pairs; no
median-only gate.**

- Apply the preregistered `GATE_MIN_LINE_SNR_DB` **per microphone and per frame**, producing a
  boolean mask over (mic, frame).
- Require at least `GATE_MIN_FRAMES` **usable** samples (not the clip's total frame count).
- Form each lag cell **only from pairs whose endpoints both lie inside the same continuous run of
  valid frames** for that microphone. There is already a `_runs` helper in `phase_stats`; reuse the
  same idea rather than writing a second one, and do not invent hysteresis or a crossing graph.
- The preregistered gate constants themselves do **not** change. Only where and how finely they are
  applied changes. Record in the moment diagnostics how many (mic, frame) cells and lag pairs
  survived, so a later reader can see the gate bite.

## 7. Unidentifiable dynamics must stop before the MAP (P2, CLI)

## 8. `state_grid_convergence` is NOT convergence — rename it (P1)

The exported diagnostic evaluates only the middle frame of the first clip and builds its "coarse"
result by **subsampling the already-fitted MAP path**. It never optimizes or predicts from a
refined grid, so it cannot establish convergence under refinement, and a path that omitted
recoverable subwindow motion can report an arbitrarily small change.

Main's minimal choice: **rename it accurately and do not gate on it.**

- Rename the export key and the function to `coarsening_sensitivity` (and the CLI's printed line),
  and reword the text so it says exactly what it measures: the sensitivity of one frame's predicted
  spectrum to coarsening the fitted MAP path, which is a sanity indicator only.
- State explicitly, in the docstring and in the exported note, that it is **not** a convergence
  result and must not be used for acceptance.
- Record in the export the note that the real check — a matched planted fit/prediction comparison
  at 500 vs 1000 Hz — is run in the verification phase, and that **if the real fitted parameters
  fall outside the validated range the export must be flagged as needing real grid refinement

- The existing planted two-sided grid test stays as it is: it is a genuine planted
  prediction-vs-grid comparison, not the export diagnostic, and it is not what is being renamed.
  Update any reference in it or in the docstrings that calls the exported value "convergence".

## 9. The floor, done coherently — Main's directive, SUPERSEDES the previous pass

The previous pass was told to fix the floor with the `[1/6, 2/3, 1/6]` Hann power kernel plus a
`w^2`-weighted speed exposure. Main has replaced that with a single coherent treatment that reuses
machinery you already have. **Implement this instead**; if the previous pass already landed the
three-tap version, replace it.

Treat the coloured Gaussian floor as a **proper complex process**: a complex process whose
covariance is `2 * R_floor` has a real part with covariance `R_floor`. So call the existing
`expected_periodogram_from_atoms` with

- a **real** atom `a_t = w(t) * A_floor(t)` on the work grid — `w` the periodic Hann of length
  `n_fft_work`, `A_floor(t)` the floor amplitude envelope evaluated **sample by sample**, exactly
  the envelope the renderer applies (so the nonlinear `floor_exp` within a ramp window is carried
  exactly, not by an exponent of a rectangular mean rate);
- `r_tau = 2 * R_floor(tau)` on the work lag grid;
- the same oversampling and transfer normalization as the lines (`Fs_analysis / Fs_work`, head
  slice of the first `n_fft//2+1` bins, transfer applied once).

This is exact and it costs nothing new: it gives you the coloured floor's Hann window response AND
the within-window amplitude variation without any dense `(T, T)` operator and without a single
extra stochastic state. Verify the factor of 2 for yourself before you rely on it — with a real
atom the kernel's image fold makes `P_Z(-f) = P_Z(f)`, so `M = 0.5 * P_Z / sum(w^2)`, and
`r_tau = 2 R_floor` is exactly what turns that into
`sum_{t,s} w_t w_s A_t A_s R_floor(t-s) e^{-2 pi i f (t-s)} / sum(w^2)`. Write that one-line
derivation into the docstring.

`R_floor` comes from the **actual renderer's PSD convention by FFT, once per optimization step**
(it depends on the fitted floor shape, so compute it with `torch.fft` inside the graph, not with a
detached numpy call). Normalize so the level lives in `A_floor` and the shape in `R_floor`: take
the autocovariance `c(tau)` as the inverse FFT of the floor PSD on the work grid, use
`r_tau = 2 * c(tau) / c(0)` and fold `sqrt(c(0))` into `A_floor(t)`. The **same** PSD function must
be used by the renderer to synthesize the floor — one source of truth, so fit and render cannot
drift. Pin the whole thing with a planted **coloured** floor, not only a flat one: a flat floor is
invariant under the window response, which is exactly why the old regression could not see the
defect.

If for some reason you cannot make the kernel route work and fall back to the three-tap Hann plus
weighted-variance approximation, you must **label it as an approximation and quantify it on a
coloured floor with a ramp** (not on a flat floor), and report the number. Do not present it as
exact.

## 10. One shared positive-rate convention, and honest off-regime reporting

Main's ruling on the zero-speed defect, which is narrower than "clamp it":

- Use **one shared positive-rate convention in fit and render** — a single module constant, applied
  identically in both paths. At minimum this must make an inconsistent `0 ** negative` impossible,
  in both directions (the model currently clamps at `1e-6`, the renderer clamps `f0` at exactly 0
  and then raises it to a possibly negative fitted exponent, which is a non-finite render from a
  finite-looking export).
- The **calibrated domain is rotors at or above 20 rev/s**, i.e. standby, ramp and cruise. Do not
  invent credible motors-off physics by extrapolating a negative fitted exponent down to zero.
- When an input trajectory goes below the calibrated domain, **report it** as unsupported
  off-regime extrapolation — a named diagnostic in the export / render diagnostics, and a message —
  rather than silently producing a number. The clamp exists to prevent infinities, not to pretend
  the model covers a stopped rotor.


## 11. Memory, chunking and phase centering on the 4x grid (Main)

The 64 kHz work grid quadruples the FFT working set. Main's rules:

- **Never reduce `k_cap` and never drop orders to fit memory.** Dropping orders is the masking the
  user rejected; memory is an implementation problem, not a modelling one.
- Keep `frame_chunk = 1`. If that is still too large, reuse the **project's existing harmonic-chunk
  (32) + `torch.utils.checkpoint`** pattern — read how the existing code already does it and follow
  it rather than inventing a second scheme. An optional harmonic checkpoint is a numerical
  implementation detail, not a new scientific model and not a candidate round. Make it a plain
  config switch (e.g. `harmonic_chunk: int | None`), defaulting to whatever keeps a V100 16 GB
  within budget.
- **Phase centering per window, before multiplying by `k`.** Subtract the window's own reference
  phase in float64, then form `k * (Phi(t) - Phi_ref)` in float64, wrap into `[0, 2 pi)` in
  float64, and only then cast to float32. A constant phase offset per (window, order) cancels
  identically in `|X(f)|^2` and in the atom autocorrelation, so the expected-power gauge permits
  it and it adds no stochastic structure — it just stops a large angle from being rounded in
  float32. Say in a comment why it is exactly gauge-free, so nobody "restores" the absolute phase.
- Do **not** benchmark anything now. Main will run, after all edits settle and remotely, one full
  `n_fft = 16384`, `hop = 1024`, `K = 230`, `R = 4`, `M = 8` forward+backward GPU memory/time smoke
  before any real fit. Your job is to make that smoke possible, and to keep the cost arithmetic in
  the module docstring updated for the 4x grid so the measured numbers can be checked against it.
