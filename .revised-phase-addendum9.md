# Addendum 9 — composite temperature, floor convention, and the legacy/candidate unit relation

Precedence: addendum 9 > 8 > 7 > 6 > 5 > 4 > 3 > 2 > addendum > brief. Most of Main's latest

## 45. `composite.temperature` — Main's APPROVED scalar rule (implement exactly this)

Addendum 5 §28 told you to keep the fit temperature separate from exposure bookkeeping. Main has
now approved the exact algorithm. It is a **simple scalar rule, not optimizer tuning**, and it
must be settled **before** any candidate fit.

Using the **global log-power-gain score** on fixed calibration supports, over legacy-baseline
predictive draws `b`:

```
U_b = sum_i a_i * (1 - I_b / M_i)      # gain-direction score, draw b
H   = sum_i a_i                        # total exposure weight
J   = sampleVar_b(U_b)                 # across-draw sample variance
T   = J / H                            # frozen composite temperature
```

so that `L/T` plus **one** OU prior matches the gain-direction sandwich variance.

Rules, all mandatory:

- The index `i` runs over **every in-band mic and bin**, using the **exact same analysis exposure
  weights** `a_i` as the composite itself (addendum 5 §28). No separate weighting.
- **No gain normalization per draw.**
- **One fixed master seed** with a **preregistered** number `B` of *internal predictive MC draws*
  — these are **not** model-training seeds. **Propose `B` (e.g. 16) and the calibration clip set
  BEFORE executing.**
- Estimate **per rig**. For Michael's equal-regime risk, use the **same weighting** in `U` and
  `H` as the gate uses.
- Label the result **scalar gain-direction calibration only** — explicitly *not* posterior
  calibration in every parameter direction. Put that wording in the record.
- If `J <= 0` or non-finite: **FAIL the calibration.** No arbitrary clamp, no fallback value.
- Calibrate through the existing baseline/physical renderer, **after the units question is
  resolved** (addenda 4 §24, 7 §38, 9 §46-47), and **remote only** — no heavy laptop work.
- It must **not** be trainable and must **not** be tuned after seeing candidate results
  (addendum 3 §20).

**Return the concrete clip list, `B`, the master seed and the resulting `T` value to Main for
freeze before the candidate fit**, recorded in `docs/revised-phase-baseline-proposals.md`. A rule
plus actual numbers, not a description.

### 45a. Which weights `U` and `H` use — ONE global convention

This is the easiest way to get §45 silently wrong, so it is stated separately.

- `U_b` and `H` **must** be computed from the **actual UNNORMALIZED `composite_risk` weights** —
  **not** from the per-second-normalized reported score. Using the normalized reported `L` makes
  the priors wrong **by duration**.
- The fit-loss weights are `a_i = hop / nfft`, with the **analysis-duplicate split** of addendum
  5 §28 applied. `H = sum of a_i over ALL mic/bin/frame entries`.
- If you do compute `U` from a normalized reported `L`, you **must** rescale `T` accordingly
  before exporting it to the fit. Either path is acceptable arithmetically; silently mixing them
  is not.
- **Freeze ONE convention globally. There must not be two temperatures.** Record which
  convention is frozen in `docs/revised-phase-baseline-proposals.md`.
- Direction of application: the fit divides, i.e. **`L / T`** with `T = J / H` exactly as in §45.
  (The candidate code previously *multiplied* by `temperature`; its owner has been instructed to
  divide and to keep the same public field name. Expect the field name `temperature` to persist
  with the corrected meaning — do not introduce a second differently-named field.)

## 46. Physical floor is defined at the 16 kHz analysis convention

The candidate's physical floor is defined at the **16 kHz analysis convention**, with the native
white-floor compensation `sqrt(F_native / F_out)`. This **must be verified on a pure floor**
(not inferred from a mixed signal). It is the same effect as addendum 7 §38 / addendum 8 §43:
keep it separate from `normalize_rms`, which moves tones and floor together.

## 47. Legacy vs candidate profile units — the exact factor

The two families' profile units differ by a fixed, now-stated factor:

```
P_candidate = 2 * P_legacy_physical / 16000
```

Apply it **only** if a value is ever seeded across families. **Never copy `profile_db` between
families blindly** — this is the concrete form of the addendum 7 §38 warning, and the numeric
relation to use if any cross-family seeding or comparison happens at all. Prefer keeping the two
adapters on wholly separate declared units so the factor never has to be applied silently.
