## P1-A — remove the whole-frame harmonic mask (the user explicitly rejected masking)

`_RevisedModel.frame_model` decides `live` from `k * frame-mean(raw + b) <= 7900` and zeroes the
**entire** time-domain atom for that order. In a ramp window where `k f(t)` straddles the band
edge, a frame-mean a hair above the edge discards samples whose harmonic is genuinely inside the
band, and a hair below keeps the whole out-of-band segment. It is a discontinuous, wrong prediction
exactly at band-edge crossings, and it recreates the masking the user dropped.

**Remove the mask entirely** — do not relax its threshold. Every order `k = 1..k_cap` contributes
its actual within-window time-varying atom, always. Out-of-band content is then handled by the
work-grid synthesis and the known transfer (P1-B), which is what physically removes it.

Replace it with a **domain check that fails loudly, never drops silently**: if any
`k * f0_r(t)` (including the MAP/fresh `nu` excursion, not just the raw telemetry) reaches
`sample_rate_work / 2`, raise a `ValueError` naming the rotor, the order and the offending
frequency. At `k_cap = 230` and observed carriers below ~110 rev/s the maximum is ~25.3 kHz against
a 32 kHz work Nyquist, so a real clip never trips it; an out-of-domain export must stop, not be
quietly truncated. Same rule in the renderer: its current
`if float(np.max(k * f0[r])) >= nyq_native: continue` is the same silent drop and must become the
same raise. (This changes the RNG draw order in the renderer, because no order is skipped any
more — that is required, not incidental; say so in your report.)

### The kernel call on the work grid

Synthesize atoms on the work grid and window them with the **periodic Hann of length
`n_fft_work`** (`phase_kernel.hann_window(n_fft_work)`), then

```
S_work = expected_periodogram_from_atoms(atoms_work, r_tau_work, n_fft=n_fft_work,
                                         window_sumsq=sum(w_work**2))
```

`r_tau_work` is `R(tau)` on the **work** lag grid (`tau = 0..n_fft_work-1` at `1/sample_rate_work`).

Because `Fs_work / n_fft_work == Fs_analysis / n_fft_analysis`, the returned bins are **already on
the analysis frequency grid**: retain the **FIRST `n_fft // 2 + 1` bins**. This is a head slice.
It is **NOT** a subsample of every 4th bin — getting that wrong is the obvious way to produce a
plausible, wrong spectrum, so put the reason in a comment.

Then convert to output periodogram units by the factor `Fs_analysis / Fs_work` (= 1/4), because the
kernel divides by `sum(w_work**2)` and a tone's kernel output scales with the window length. **Pin
this factor with a planted tone in the tests rather than trusting the derivation.**

### The known transfer

Apply it **EXACTLY ONCE** in the candidate's expected spectrum: once in the fit's `frame_model`

Attribution, get this right in the docstrings: the AA is flat to 0.000 dB through 7900 Hz within
its 0.01 dB ripple spec and -100.4 dB at 8000 Hz; the **~4.9 dB at 7900 Hz is the `resample_poly`

### Label the approximation honestly

This multiplier is a **WINDOW/FILTER-COMMUTATION APPROXIMATION**, not an exact moving-filtered
periodogram: in the real renderer the filtering precedes the Hann window. Say exactly that, in the
module docstring and next to the call site, alongside the statement that the finite-window kernel
is otherwise exact. Do **not** add a dense covariance operator or any "exact filtered periodogram"
machinery — Main's accuracy gate decides whether the approximation stands.

### Why applying it inside the FIT is self-consistent (put this in the docstring)

The fit sees real 16 kHz data `D` and models `M = T * S(params)`, so it learns `S` with
`T * S ~ D`. The renderer synthesizes `S` on the work grid and then physically applies `T`, so the
synthetic arm reproduces `D` in the analysis band whatever the real clip's own 44.1 kHz history
was. The consequence, which must be stated plainly rather than left for a reader to trip over:
`S` — and therefore `profile_db` — is **not** a calibrated absolute source spectrum; it is the
source-side quantity of this declared observation chain.

### The renderer's floor

scalar, but the frequency-dependent part now comes from the transfer, so make sure the floor is
synthesized on the work grid such that **after** the real AA + decimation it reads the
analysis-unit floor the fit uses. State in a comment that the scalar alone was never enough (that
was exactly the defect) and that the shape is now carried by the transfer.

## P2 fixes (NumericsReview, all confirmed real)

1. **`phase_kernel.py` mixed-backend device.** The torch branch builds `atoms` first and then moves
   `r_tau` onto `atoms`' device. With numpy `atoms` and a CUDA (possibly grad-carrying) `r_tau`,
   the only real tensor is dragged to CPU and the result comes back on the wrong device. **Select
   the device/dtype from whichever argument already IS a tensor, before converting the other.** The
   public API, the algorithm and every documented convention stay identical — this is an internal
   dispatch fix. Add a regression test for the numpy-atoms + tensor-`r_tau` direction (CPU is
   enough to pin the selection logic; skip the CUDA leg when unavailable).
2. **`prior_r_tau` must dispatch on `k` too.** It picks its backend from `tau_s` and `d` only, so a
   torch `k` with numpy lags falls into the numpy branch and either raises on a CUDA tensor or
   silently drops autograd. Include `k` in the backend selection and convert the other inputs onto
   its dtype/device.
3. **`simulate_state` with `S == 1`.** `inc` is empty, so `zeros_like(inc[..., :1])` is empty and
   `theta` comes back length 0 while `nu` is length 1, violating the same-grid contract. Seed the
   `theta_0 = 0` gauge from a **length-one slice of the state grid** (e.g. `zeros_like(nu[..., :1])`)
   so a one-sample grid returns `theta` of length 1. Add the length-one regression.
4. **Zero-speed convention must match between prediction and rendering.** The fitted model
   evaluates both speed laws at `rate.clamp_min(1e-6)`; the renderer clamps `f0` at exactly 0 and
   raises that zero to the unconstrained fitted `amp_exp`/`floor_exp`, so a negative exponent plus a
   stopped rotor gives non-finite audio while `predict_spectrum` stays finite. **Use one shared
   positive speed floor constant in both paths** (a module constant, e.g. `SPEED_FLOOR_RPS = 1e-6`,
   referenced by prediction and rendering alike). Do not add a parameter.
5. **Apply the analysis-window response to the coloured floor.** The kernel's harmonic shapes
   already carry the periodic-Hann finite-window response, but `_floor_frames` is added as if its
   per-frequency physical spectrum were the observed periodogram. For a coloured floor the expected
   Hann periodogram is the intrinsic spectrum convolved with the same `[1/6, 2/3, 1/6]` power kernel
   `model.py` uses (`model.HANN_POWER_KERNEL` — import it, do not retype the numbers). Apply it
   along the frequency axis with sane edge handling, and say in a comment that a flat floor is
   invariant under it, which is why the existing renderer regression could not see the defect.
6. **Floor speed law must use the within-window exposure.** `_floor_frames` raises one rectangular
   frame-mean rate to the fitted exponent, while the renderer applies the exponent sample by sample
   and the analysis then sees it through `w(t)^2`. For a ramp and a nonlinear `floor_exp`,
   `(mean rate)^p != sum(w^2 rate(t)^p) / sum(w^2)`. **Compute the floor exposure as the
   `w^2`-weighted within-window average of `rate(t)^p`**, i.e. the same envelope the renderer
   produces. Reuse the frame machinery already there; do not build a second framing helper.
